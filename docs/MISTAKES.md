## NOTCH-20261117-QUESTION-OPTIONS · 17 November 2026

- Request. When any session asks a question with several choices ("rather than approve or deny… it shows four options and asks us to select"), the notch must unfold and offer those options as buttons in the tab itself, so the user picks one there and it is sent back to the tool.
- Where the choices come from. Claude Code's `AskUserQuestion` rides the ordinary `PreToolUse` hook like every tool, so the settings the users already pasted keep working unchanged: `src/main/agentStatus.ts` now inspects the permission payload before treating it as approve/deny. `tool_input.questions[]` with `options[]` (or a generic top-level `options`/`choices` array) is parsed into a held question — up to 6 options, label + description, `multiSelect` honoured — instead of an approval. An explicit `kind=question` hook also exists for other tools. The held HTTP connection is the same mechanism approvals use (hold 10 minutes for questions); if nobody answers, the hook replies `{}`, the hook's own 250 s timeout has long since let the tool ask in its window, so nothing can wedge the agent.
- How the answer travels. Hook output cannot select an option, so the chosen labels ride back as the PreToolUse block reason: `permissionDecision: "deny"` with the reason "In answer to \"…\", the user chose: SQLite (…). Treat this as the user's answer and continue without asking again." Codex and Cursor answers use their own deny-with-message shapes (`decisionForQuestion`). Worst case on an older tool build is a normal deny — the agent reads the reason and moves on.
- Surfaces. The collapsed tab grows a `has-question` strip (widest of the three morphs: 560 px) with the asker, the question and up to four option pills; single-select answers on tap, multi-select shows "Multiple choice — open to answer" and opens the panel. The expanded Sessions page gets a `QuestionCard` above approvals with descriptions, toggle-to-pick and a "Send answer (n)" button for multi-select, plus "Answer in the tool instead" which releases the hold. On a first-seen question the notch auto-opens onto Sessions (per the request) with a chime and a toast; hover-open stays blocked while a question waits, like approvals.
- Verified live, on the running app, not just in the module. `scripts/check-agent-questions.cjs` covers the bridge (detection on the permission hook, parsed options, the answered reply text, multi-select joining, release, plain permissions untouched, bad choices rejected while held) — and `node scripts/check-agent-status.cjs` still passes, so approve/deny is regression-free. Then the real loop with the built app: an `AskUserQuestion` payload POSTed to the live bridge → the notch auto-opened on Sessions with all four options → collapse → the tab showed the four pills → CDP click on "SQLite" → the held hook HTTP reply carried `SQLite (Zero setup, single file)`. A second pass exercised multi-select (tab shows the hint; two picks sent as one answer). The first question that arrived while the notch sat idle on the user's desktop was answered by the user themself from the notch — the event the feature was built for happened before the test even ran.
- Trap for next time. This environment exports `ELECTRON_RUN_AS_NODE=1`; `electron.exe` then runs the main script as plain Node (`electron.app` undefined, exit 0, nothing in the log). Clear it for PowerShell (`$env:ELECTRON_RUN_AS_NODE=$null`) before launching the app for a live test.

## NOTCH-20261117-IDLE-COMPUTE · 17 November 2026

- Report. "This notch should not use heavy compute … it really makes the entire computer slow." Measured before touching anything, in the running dev app on the 12-core laptop: the whole tree (4 Electron processes + 2 PowerShell hosts) idled at **0.51% of the machine**, and two long-lived PowerShell children held ~165 MB.
- The worst offender was not Electron. `foreground.ts` ran a PowerShell-language loop every 800 ms that called `Get-Process -Id` (and `Get-Process -Name` for the browser probe) and rebuilt a hashtable plus a JSON document per tick. Benchmarked in isolation that is **1.125 s of CPU per 30 s — 3.75% of one core, permanently**, plus .NET GC churn in a 79 MB shell all day, to answer a question ("is the foreground window fullscreen?") that is four Win32 calls.
- Fix. The shell still hosts the loop, but the tick is now one call into a compiled C# sampler (`Add-Type`, `GetForegroundWindow`/`GetWindowRect`/`IsZoomed`/`GetWindowThreadProcessId`, process name cached per pid, browser sweep throttled to 5 s and skipped when browser-only mode is off), serialised by hand. Same `{process, fullscreen, own, browserOpen}` contract: **0.141 s per 30 s, 0.47% of one core** — 8× less — and in the live app the child now measures 0.00–0.03% of a core.
- Media monitor (`localMedia.ts`). WinRT metadata cannot be projected from C# under PowerShell 5.1, so that loop has to stay in a shell; it now ticks at 1.5 s instead of 1.1 s and sleeps with `[Thread]::Sleep` instead of the cmdlet (0.78% → 0.08% of one core measured live, still emitting identical JSON).
- Session scans were the spike. A scan starts a PowerShell that enumerates every process (~0.28–0.30 s CPU, ~90 MB transient), then re-reads each agent store. The renderer re-ran `refreshSessions()` whenever `expanded` flipped, so **opening and closing the panel each bought a full scan**, right after the timer had already scanned. Now: a scan on mount, an open only re-scans when the snapshot is older than 15 s, and the cadence is 30 s open / 120 s collapsed / 180 s hidden (was 15/60/120). Process enumeration is also cached 20 s (failures are never cached, or every tool would read "closed").
- Unbounded file reads. `scanVsCodeFamily`, `scanGemini` and `scanCline` parsed *every* chat log every scan — a busy editor keeps thousands of them and each file is a whole conversation. They now stat everything, sort by mtime, parse only the newest 12, and read at most 2 MB of a file for a title (same "stat, then read the newest few" shape Claude scanning already used).
- Renderer. The four endless liquid keyframes (plus a `mix-blend-mode` sheen) kept the compositor busy behind a parked, invisible panel on a full-screen always-on-top surface; they are now `animation-play-state: paused` while collapsed. `MediaProvider` subscribed to the 1 s clock unconditionally just for the progress bar, re-rendering every consumer once a second with no track playing; it is now `useNowWhen(playing)`. The player poll is 3 s while collapsed (progress is extrapolated from the last sample) instead of 1 s. Posture capture dropped from 640×480 to 480×360 (the lite model works at 256) and its tiers went 180/900/120 ms → 220/1200/150.
- Result, measured the same way: idle **0.13% of the machine**, ~4× lower, with the PowerShell children effectively asleep. Remaining known cost: two shell hosts (~150 MB together) that could be merged into one; the media one cannot be removed, since SMTC metadata needs a WinRT projection that only the shell has.
- Trap for next time. `Get-Process -Name electron.exe` returns nothing — `-Name` matches `ProcessName`, which has no `.exe`. That, not a missing process, is why a first benchmark printed zeros.
- Capture note. `NOTCH_CAPTURE` verification needs `ELECTRON_RUN_AS_NODE` unset; with it set, `electron.exe` runs as plain Node and `require('electron').app` is undefined, so the capture path dies on `disableHardwareAcceleration`.

## NOTCH-20261117-SESSIONS-SCROLLBAR-FIX · 17 November 2026

- The entry below was wrong about the root cause, and the user pushed back correctly: the tool column did not scroll, it was just clipped, and its height looked shrunken.
- Real cause. `.sessions-page` declared only `grid-template-columns`, so the implicit row was `auto`. With tall content the row grew past the page, the columns grew with it, and the page's `overflow: hidden` cut everything at the window edge. Styling the thumb (the previous attempt) was fixing the wrong half.
- Fix. `grid-template-rows: minmax(0, 1fr)` on `.sessions-page`, so the row is bounded by the page, which gives both columns a real height; `.sessions-apps-list` then scrolls its cards and `.sessions-scroll` scrolls the session list, each with the slim light-gray bar.

With `.agent-card { min-height: 108px }` injected into the harness at 1120×520: `.sessions-page` is 458/458 (nothing clipped), `.sessions-apps-list` is 920 content in 364 of box (`scrollable: true`), and the session list scrolls too; the capture shows a bar in both columns.
- Lesson. "No scrollbar" is a layout question first — check whether the scroller has a bounded height before touching scrollbar styling.

## NOTCH-20261117-DELIVERY-FALSE-NEGATIVE · 17 November 2026

- User report and evidence. The message arrived in the tool while Notch said it had not been sent, and the composer kept its sending state. The message was visibly in the session, so both statements were wrong.
- Verified cause. `settle()` verified the store only when the CLI exited 0 with no error JSON; every other exit went straight to `failed` → “did not deliver”. An agent CLI routinely exits non-zero *after* accepting a message (a turn interrupted, a stream that broke, a daemon that answered late), which is exactly a delivered message reported as a failure. The composer also only left “sending” when the process ended, so a CLI that streams a whole turn (OpenCode does) held the spinner long after the message arrived.
- Correction. The store decides in every case: a confirmed match reports `delivered` even when the exit code and the printed error say otherwise, and a refusal at dial level is the only case that skips polling because nothing can have arrived. While the command runs the store is polled every 1.2 s for up to 45 s, and the send is reported the moment the text is there instead of waiting for the process.
